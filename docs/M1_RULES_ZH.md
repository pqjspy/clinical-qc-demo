# M1：先认识这份虚拟规则库

这些规则全部是我们为 Demo 编写的。它们不是医院标准，不是医学建议，也不是通用临床试验要求。`demo_approved` 表示“在演示中模拟已经发布”，不表示任何机构批准。

## 从 QC002 开始看

你输入的是事实：“同一样本，10:06 采血，10:33 开始离心。”

系统另从规则库找到：“本虚拟方案要求至少 30 分钟。”

代码之后才能计算 `27 < 30`，形成待人工复核的建议。本阶段建立事实之外的规则资料和分类名称；还没有让模型理解文字，也没有建成规则执行器。

三个文件各管一件事：

| 文件 | 你可以把它理解成 | QC002 的内容 |
|---|---|---|
| [taxonomy.json](../data/knowledge/taxonomy.json) | 允许使用的分类名称表 | 样本管理 → PK 样本管理 → 样本处理时间不足 |
| [protocols.json](../data/knowledge/protocols.json) | 可供点击查看的虚拟原文 | “从采血到开始离心……至少为30分钟” |
| [rules.json](../data/knowledge/rules.json) | 从原文整理出的机器可读规则 | `minimum_minutes: 30`、必需两个时间、建议中风险 |

三者分开，才能核对“参数是否有原文依据”“分类是否真的存在”，而不是模型说一个新名字就算通过。

## 六个分类，不是所有问题必须硬塞进去

| L3 ID | 一级 → 二级 → 三级 | 真正要核对的事实 |
|---|---|---|
| `L3-PK-001` | 样本管理 → PK 样本管理 → 样本处理时间不足 | 同一样本的采血与开始离心时间 |
| `L3-VISIT-001` | 试验实施 → 访视管理 → 访视超窗 | 锚点日期、锚点日号和实际访视日期 |
| `L3-AE-001` | 安全性管理 → 不良事件记录 → 不良事件漏记 | 事件存在、登记册完整、条目不存在是否都已明确 |
| `L3-DRUG-001` | 试验用药管理 → 库存与台账管理 → 试验用药账物不一致 | 同一结算范围的期初、入库、发放、退回和期末实盘 |
| `L3-ROLE-001` | 人员管理 → 授权与职责管理 → 操作超出授权范围 | 操作人、授权对象、操作范围和授权时点 |
| `L3-EDC-001` | 数据管理 → 原始记录与 EDC 一致性 → 原始记录与 EDC 数据不一致 | 先对齐受试者、字段、时点、单位，再比较值 |

每个 L3 有一个 L4 候选帮助说明细节。L4 不是自动确认结果。正常、资料缺失、规则冲突或不支持的输入，都可以没有 L3；它们是处理状态，不是额外的违规分类。

## 一条规则怎么读

以 `SYN-RULE-PK-001@1` 为例：`@1` 表示规则版本 1。

- `scope`：只给 `SYN-STUDY-001`、`SYN-SITE-A` 和 `SYN-PROTOCOL-001-v1` 使用，并且事实发生时点要在生效区间内。
- `required_facts`：`collected_at`、`centrifuged_at`、`same_sample`。任何一项不明确，都不能靠猜来算。
- `check_type`：`elapsed_minimum`，意思是以后交给“检查最小时间间隔”的代码。
- `parameters`：最小间隔 30 分钟，不是写在模型记忆里的数。
- `output_l3_id`：命中时只能指向分类表中的 `L3-PK-001`。
- `risk` 与 `suggested_decision`：这份虚拟规则配置了“中”和“方案偏离”；二者仍是建议，须人工确认。
- `source`：文档 ID、段落 ID、逐字原文。引用文字必须确实存在于对应段落。
- `supersedes`：明确替代哪个旧规则版本，而不是“文件更新得晚就更权威”。

其他五类的建议判定为“需人工判定”。例如发现两张表的值不一致，并不能仅凭这一点把所有 QC 问题都宣布成方案偏离。

## 为什么有 9 条规则，却只有 6 个三级分类？

不是一条规则就必须新建一个分类。我们有：

1. v1 方案的六条正常演示规则，对应六个问题家族。
2. v2 的一条 PK 更新规则：从 2026-10-01 起把该虚拟研究的最小间隔改为 20 分钟。
3. 独立冲突研究的两条故意矛盾的规则：相同范围和时段，分别要求 30 和 20 分钟，无替代关系。

所以 `6 + 1 + 2 = 9`。冲突规则只属于 `SYN-STUDY-CONFLICT`，不得混入正常研究的可执行集合。它们故意保留 `demo_approved`，用于模拟“元数据都声称已发布，但业务条件互相冲突”的坏输入；真实导入流程应阻止这种配置发布。

三份文档分别是正常 v1、正常 v2、冲突方案。v2 只提供 PK 条款用于版本演示，不代表其他五类在 v2 也已经有适用规则。

## 两个最容易算错的边界

**生效时间采用半开区间：包含开始，不包含结束。**

v1 是 `[2026-01-01 00:00:00+08:00, 2026-10-01 00:00:00+08:00)`；v2 从后一个时点开始，没有配置结束时点。在 10 月 1 日零点，不能还套用 v1。所有带时间的值都明确 `+08:00` 时区；访视按自然日计算，不把日期当时分秒做近似换算。

**第 1 天不是相差 1 天。**

访视规则将锚点日期本身算第 1 天，所以实际日号是 `日期差 + 1`。目标第 28 天，允许 ±7 天，就是闭区间 `[21, 35]`；第 21、35 天都在窗口内，第 36 天在窗口外。

## 六种计算的输入约定

这里是下一步实现代码要遵守的契约，不是已执行结果。

| check_type | 判断方式与不能猜测的地方 |
|---|---|
| `elapsed_minimum` | `开始离心 - 采血 < minimum_minutes` 才命中；不能把负时差、不同样本或不明确时间正常算下去 |
| `visit_window` | `actual_visit_date - anchor_date + anchor_day_number`；本规则要求锚点日号为 1，窗口端点包含 |
| `explicit_absence` | 只有 `event_present=true`、`register_complete=true`、`entry_present=false` 才能认定本规则的漏记；`urgent_flag` 只是输入中的明确紧急线索，不是医学严重性推断 |
| `inventory_balance` | 比较 `opening + received - dispensed + returned_to_stock` 与 `closing`；全部是非负整数，单位、药品和期间须一致；`returned_to_stock` 不是所有回收药物 |
| `authorization` | 比较操作人和授权对象、清单中是否含此操作，以及 `authorized_from <= operation_at < authorized_to`；没有授权材料不能当成已经确认无授权 |
| `aligned_value_match` | 先检查两侧 subject、field、timepoint、unit 一致，再精确比较 value；不同单位不在本版自动换算，缺值不当成相等 |

库存规则另外要求 `inventory_scope_confirmed` 布尔事实，必须有原文证据支持同药品、中心、单位和期间已经对齐。`alignment_required` 只是对范围的说明，不因存在这段配置文字就算已经验证；M2需要核对该事实与证据。结构正确不等于业务事实正确。

最后记住：**分类表决定叫什么，方案原文说明为什么，规则参数供代码计算。** 案例里的参考答案另存，绝不能当成检索知识喂给模型。当前材料用于学习、构建和测试 Demo，不证明真实医院数据上的准确率。
