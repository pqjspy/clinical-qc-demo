# M3：从命令行变成可以复核、保存的网页

这一步先不增加新的医学/质控场景。你已经见过 Qwen 说错“符合/不符合”，现在我们给这条真实流程加一个能操作的工作台。

## 先实际做一遍，不先读框架

打开本机网页：<http://127.0.0.1:8911>。账户密码在本项目 `runtime/web/local_accounts.json`，这是首次启动时生成的本机演示密码，已排除在 Git 外。选择 `reviewer`，复制对应密码登录。不要把此文件上传或把网页公开。

1. 在“质控记录”选 **QC002**，先读左边的真实合成原文：10:06 采血、10:33 开始离心。
2. 点击“运行本机 Qwen”。页面会说明目前在抽取事实、查规则还是生成解释；这两次模型调用仍可能需要十几秒或更久，不承诺几秒。
3. 在右边看 **程序确定结果：27 < 30**，点击 `[F5]` 定位原文中的采血时间。`[R1]` 是当时使用的虚拟方案原文，完整显示在证据区。
4. 继续看“Qwen 解释草稿”。如果仍写“符合至少30分钟规定”，就在“人工解释”里改掉。这里修改的是人工意见，不是偷偷修改模型历史。
5. 填写操作理由，勾选核验声明，点击“保存新的复核版本”。会保存为 v1。
6. 刷新网页或从“人工复核”队列重新打开。上方仍是原初判/原草稿，下方是人工 v1。

本次自动化验收保存的意见，理由中明确写了“浏览器验收”；它不是专业临床人员的审核，也不是对真实患者的结论。你可以再追加自己的学习复核 v2。

## 三种操作有什么区别？

| 操作 | 具体含义 | 会不会改掉 AI 原结果？ |
|---|---|---|
| 确认原初判 | 你已核对程序结果和原解释，原样保存成人工确认版本 | 不会 |
| 编辑人工意见 | 可以修改人工分类、风险、判定、解释与措施，必须说明理由 | 不会，另存新版本 |
| 退回补充 | 信息或结果不足，保留待补充状态，不确认“有/无问题” | 不会 |

“确认原初判”不是确认你上一次编辑的版本：它明确指上方原初判。若要保留或继续修改人工意见，使用“编辑人工意见”。失败/未决分析不能一键确认原初判；可以退回，也可以明确记录人工作出的独立意见，后者标记为人工编辑而不是 AI 预测。

正常40分钟也要复核，因为程序只检查这一项，且自然语言抽取和解释仍可能错误。保存/关闭提醒不是宣布整个研究合规。高风险/未决的初始建议仍保留，人工降低风险必须有理由。

## 改一个条件，观察区别

选择 `SYN-EXERCISE-40`：其原文已经是10:06至10:46。不要只改页面上的事件时点，必须看原文中的时间。原文才是抽取来源。

## 三个角色不是三个模型

| 账户 | 允许做什么 |
|---|---|
| viewer | 看原文、运行、证据、复核和历史；不能写入 |
| reviewer | 新增合成记录、分析、确认/编辑/退回、标记提醒 |
| rule_admin | 看记录；创建规则草稿并人工发布；不能代替reviewer签字 |

角色由后端会话确定。即使绕过网页直接请求接口，查看者也不能提交审核。密码是本机演示账户，不是医院身份系统。服务重启或8小时后需重新登录；数据不会因此消失。

## 规则库：草稿不等于已生效

用 `rule_admin` 登录，打开“规则库”：

1. 读现有9条版本，包含原研究PK v1/v2与专门的冲突研究。
2. 点击“填入新增PK规则示例”：只在编辑框中生成 **另一个合成研究** 的25分钟规则，不改变原研究。
3. “校验并保存草稿”检查来源引用、结构、合法分类、参数、日期、替代关系和重叠；不会影响分析。
4. 展开草稿检查来源及条件，确认后点击“人工核对后发布”。新提交的分析使用新知识库快照。

程序校验不能证明文字规则的完整语义和医学正确性，管理员仍需审核。已有版本禁止覆盖/删除；M3只允许追加PK规则。新增与旧规则同范围同时段的重复PK规则，即使阈值相同也会拒绝，因为当前执行器要求唯一适用规则。

网页发布存入SQLite，不覆盖M1的JSON文件。旧 `run_m2.py` 命令仍读取M1文件；在网页中重新分析才使用网页已发布快照。两种入口的知识来源明确不同，不是规则丢失。

规则的“发布时间”与“适用事件日期”不同：发布后仍按研究、中心、方案、事件时间过滤。旧分析保持旧快照。v1闭合区间可以按契约追加后续v2；现有原研究v2结束时间为空，不能直接塞入重叠v3或篡改v2，完整规则停用/更正流程尚未实现。

## 这一步的代码怎样连起来？

```text
React 页面：点击分析 / 提交复核
       ↓ HTTP 请求
FastAPI：核验登录、角色、输入、重复提交
       ↓
原 M2 工作流：本机 Qwen → 检索 → Python → 解释草稿
       ↓
SQLite：案例 + 固定运行 + 追加复核 + 规则快照 + 审计
       ↓ HTTP 响应
React 页面：显示结果和保存后的版本
```

学习顺序只看四个入口：

1. `frontend/src/App.tsx` 的 `analyze()`：按钮如何请求后端。
2. `src/clinical_qc_demo/web_api.py` 的 `start_job()`：后端如何检查权限并提交后台任务。
3. 同文件 `run_job()`：如何调用你已学过的M2，而不是另写一个假模型。
4. `src/clinical_qc_demo/web_store.py` 的 `review()`：为什么审核和审计必须在同一个数据库事务里保存。

事务的直观含义：审核记录和“谁为什么修改”的历史要么一起保存，要么一起失败，不出现“结果改了却没有历史”。版本检查能阻止两个页面同时修改时，后一个悄悄覆盖前一个。

SQLite不是浏览器缓存。它保存在 `runtime/web/qc.sqlite3`，刷新浏览器仍在；模型原始运行还在 `runtime/runs/`。不要删除这些目录来“刷新页面”。追加限制是应用层保护，拥有本机数据库权限的人仍能篡改文件，不是监管级存储。

## 启动与验证

当前已准备依赖和前端构建，直接在项目目录运行：

```bash
cd /Users/cam/Documents/Me/clinical-qc-demo
.venv/bin/python scripts/serve_m3.py
```

然后打开 <http://127.0.0.1:8911>。保持终端运行，Ctrl+C停止本应用，不会停止旧Jupyter或Ollama。一次只启动一个M3服务，不用 `--reload` 和多个worker，以免把正在运行的分析误判为中断。Ollama使用已有的127.0.0.1:11434服务，不自动下载模型。

修改前端后，在 `frontend` 目录运行 `npm run build`；重新启动服务以首次挂载构建目录。开发时可以用 `npm run dev` 的8910页面代理到8911；交付使用8911即可，不需要一直开两个服务。

复现依赖：Python3.12环境中安装 `requirements-m3.lock`，再 `pip install -e .`；前端 `npm ci` 使用已保存的package-lock。首次安装需要网络，正常分析只调用本机模型。验证命令：

```bash
.venv/bin/python -m unittest discover -s tests -q
```

不要把测试替身的通过数当作Qwen准确率。本阶段没有独立分类评测，没有宣称真实医院准确率，也未扩展其余五类。M4再做这些。
