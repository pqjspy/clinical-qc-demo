# M5：能运行、能恢复、能讲清楚的本地交付

这一阶段不让模型突然变聪明，而是解决：明天再打开项目还能不能用？你发布的规则和人工意见是否保存了？换一个目录能不能恢复？演示时怎样讲清楚功能和边界？

先想一个具体例子：你在网页发布了一条新规则。它存进SQLite，不会自动写回最初的`data/knowledge/rules.json`。如果只保存这份JSON而丢了数据库，新规则、人工意见和运行历史都会缺失。因此这一阶段要备份“正在使用的业务状态”，不只是源代码。

## 1. 先做这两个动作

在项目终端运行：

```bash
cd /Users/cam/Documents/Me/clinical-qc-demo
.venv/bin/python scripts/start_local.py
.venv/bin/python scripts/local_ops.py status
```

第一条启动已有工作台；健康服务存在时不重复启动。第二条只检查，不分析病例、不下载模型。打开[本地工作台](http://127.0.0.1:8911)，用本机`runtime/web/local_accounts.json`里的`reviewer`登录，不把密码复制进答卷。

读状态输出时，注意：

| 项目 | 它检查什么 | 不证明什么 |
|---|---|---|
| `application` | 8911是否是本项目且能响应 | Qwen一定能生成 |
| `qwen` | 本机模型服务、名称和摘要是否匹配 | 本次分类一定正确 |
| `database` | 库完整、各表数量、当前规则快照和活动任务数 | 临床记录真实有效 |
| `files` | 本地页面和账户文件是否存在 | 已完成全面浏览器验收 |
| `frozen_m4` | 17个冻结文件是否保持原样 | 模型以后每次都输出一样 |

总`ok: true`表示这些交付前检查通过。`active_jobs`大于0表示有人正在分析，等结束再备份/停止。不要因为模型未启动就重装项目，也不要因为网页还能显示就认为后台还活着。

## 2. 做一份私有备份

分析结束后运行：

```bash
.venv/bin/python scripts/local_ops.py backup
```

命令生成`runtime/backups/日期-随机编号/`，每次新建，不覆盖。复制数据库时用SQLite备份接口，能正确读到已提交的WAL内容；不是直接复制正在使用的`.sqlite3`文件。

包括：数据库（原文、已发布规则、初判、复核、审计等）、演示账户、相关完整运行轨迹、冻结18条评测及其轨迹、源代码、数据、文档、前端源文件与已构建页面。

不包括：Python虚拟环境、node_modules、模型权重、临时日志/PID、登录会话、未被网页或冻结评测引用的开发运行。它不是整台电脑的完整备份。模型和依赖需要另行准备。

重要：此目录包含明文演示密码和记录原文，只能作为私有备份，不能作为公开项目压缩包分享。目录权限限制不等于加密；SHA摘要用于查误改，不是可信签名。失败时可能留下没有`backup-manifest.json`的未完成目录，验证工具会拒绝它；工具不自动删除任何备份。

## 3. 备份成功还不够，要核对并尝试恢复

将命令输出的完整备份路径作为参数：

```text
.venv/bin/python scripts/local_ops.py verify /完整的备份目录
.venv/bin/python scripts/local_ops.py restore-isolated /完整的备份目录 --to /一个尚不存在的新目录
```

第二条命令的父目录必须已经存在，并且不能经过符号链接；macOS临时目录可用`/private/tmp/自取的新名称`。如果目标已存在就拒绝，不覆盖、不删除在线数据库。它核对文件摘要、表内容、规则版本和账户，再复制到隔离目录；本条命令本身不启动应用。

历史结果中的绝对来源路径仍保留原样，不能为“看起来更像搬家成功”重写历史。恢复后的轨迹应按`run_id`在新目录下定位。要替换真实在线环境，必须另外明确授权、先停止服务并备份当前状态；本项目刻意没有“一键覆盖线上库”命令。

## 4. 自动交付演练：一次真实Qwen，不是再跑考试

```text
.venv/bin/python scripts/verify_m5.py --backup /完整的备份目录
```

此命令创建新的`runtime/delivery_drills/日期-编号/`：先恢复备份并启动隔离应用，确认旧运行/人工意见/规则仍可读；再创建没有历史数据、没有评测答案的新应用目录，实际分析一次QC002，关闭并重建应用，核对持久化。不会往你正在使用的8911数据库插入测试记录。

演练在Python进程内禁止非回环socket连接；模型HTTP请求仅到127.0.0.1:11434。这证明应用在该限制下完成了本次运行，**不等于断开整台电脑外网**，也没有给Ollama独立进程安装网络防火墙。使用的是实际FastAPI启动/关闭和API请求，不是本轮新增的浏览器操作验证。失败保留报告，不自动重试。

结果保存在演练目录的`verification.json`。恢复启动用经过摘要核对的当前代码加载恢复数据；这是同一Python进程内重建应用生命周期，不是从备份独立启动新进程。一次QC002用于检查交付路径，不并入M4的18条评测，更不能当新准确率。已有模型权重和依赖准备完后无需为每次分析联网下载；新电脑安装与整机断网演示仍是单独验收项。

## 5. 启动、停止与常见故障

后台启动不设置开机自启或自动重启；退出登录/重启电脑后需要手动启动。日志：`runtime/web/server.log`。进程文件：`runtime/web/server-process.json`，仅供诊断，不可只凭其中旧PID停止进程。

需要前台调试时，先确认现有服务已停止，再运行`.venv/bin/python scripts/serve_m3.py`。停止前台服务用Ctrl+C。后台服务需要先通过`lsof -nP -iTCP:8911 -sTCP:LISTEN`找到监听PID，再用`ps -p PID -o pid,uid,command`核对是当前用户、本项目`/Users/cam/Documents/Me/clinical-qc-demo/scripts/serve_m3.py`，且没有活动任务，才向该PID发送一次SIGINT。不要停止Ollama或8890旧项目，不自动用SIGKILL强杀。运行中的模型请求可能需要等待超时。

| 现象 | 先做什么 |
|---|---|
| `Failed to fetch` | 不刷新丢草稿；检查网页服务。恢复后登录、查历史再决定是否重试保存 |
| 网页正常、Qwen失败 | 检查本机Ollama与指定模型，不切云模型，不自动下载 |
| 401 / 会话失效 | 先保留未保存内容，再登录；不要把旧页面当有效会话 |
| 8911被占用 | 已健康就复用；未知服务不强制关闭。现在会在数据库初始化前退出 |
| `needs_information` / 规则冲突 | 这是待处理业务结果，不是重启能修复的问题 |
| 解释引用失败或语义矛盾 | 保留规则结果，人工读证据/修改解释，不把结构合法当语义正确 |
